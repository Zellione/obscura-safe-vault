## Workflow

Standard delivery flow for every phase or feature:

1. **Implement TDD-style** — write tests first, then code until all pass.
2. **`scripts/test.sh`** — all tests green.
3. **`scripts/test.sh --asan`** — no memory/UB errors (for crypto/vault/memory changes).
4. **Open a PR** — one PR per phase; include ROADMAP and docs updates in the same PR.
5. **CI green** — all checks must pass on all platforms.
6. **SonarCloud** — use findings posted to the PR directly (do NOT install/authenticate sonarqube-cli — agents cannot complete the auth flow). Re-scan and confirm zero remaining issues.
7. **⛔ THE OWNER MERGES — NEVER THE AGENT.** When CI is green and SonarCloud is clean, **STOP**: post the PR link, say it is ready, and hand off. Do **NOT** run `gh pr merge`, push to `main`, or otherwise integrate the branch yourself — not even when every gate is green and the flow "looks done". Merging is the owner's decision, always. Green gates are permission to *ask*, never to merge. Keep follow-up fixes for a phase on that phase's branch until the owner has merged it.
8. **Post-merge verification (after the OWNER merges)** — once the owner reports the merge, `git fetch` and confirm ROADMAP.md and all doc changes are present on `origin/main`. Fix with a follow-up PR if anything is missing.
9. **Update Serena memories** — if the phase added/removed source modules, changed deps, renamed symbols, or changed conventions, update the relevant `mem:*` memory (see ## Serena below).

## Project goal

A **native encrypted photo gallery** stored in a single `.osv` vault
file. Images are decrypted **into locked memory only** — no temporary files, no
decrypted data ever written to disk. The gallery is browsable with a
freely-nestable folder tree, a big zoomable image viewer, and a thumbnail strip
navigable with arrow keys.

## Technology choices

| Area | Choice | Why |
|---|---|---|
| Language / std | **C++23** | Owner requirement — `std::span`, `<filesystem>`, concepts, designated initialisers. |
| Build system | **premake5 → Ninja** (gmake2 fallback) | Owner requirement; premake5's beta line has native Ninja support (no separate module). |
| Windowing / input | **SDL3** | Cross-platform window + renderer + file dialogs in one library. `SDL_ShowOpenFileDialog` removes the need for a separate platform layer. |
| Rendering | **SDL_Renderer 2D** (GPU-accelerated) | Textures + destination-rect scaling cover zoom/pan and the thumbnail strip with minimal code. No shader authoring needed for Phase 0–7. |
| Text rendering | **stb_truetype + baked atlas** | Header-only, trivial to vendor; bundle one OFL font in `assets/fonts/`. |
| Crypto library | **Monocypher** | Single `monocypher.c` / `monocypher.h` file, public domain. Has XChaCha20-Poly1305, Argon2id, `crypto_wipe`. Trivial to compile in premake. |
| Platform RNG | `getrandom` (Linux), `BCryptGenRandom` (Windows) | Monocypher has no built-in CSPRNG; a small platform shim in `src/crypto/random.*` fills the gap. |
| Secure memory | `mlock`/`VirtualLock` + `crypto_wipe` | Master key and KEK are held in mlock'd buffers and wiped on vault lock / app exit. Never swap to disk. |
| AEAD cipher | **XChaCha20-Poly1305** | 192-bit nonce → random nonces are safe per chunk with no counter state. Crash-safe: no nonce counter to track, persist, or corrupt. Fast without AES-NI. |
| KDF | **Argon2id** (via Monocypher) | Memory-hard, anti-GPU/ASIC. Protects the real weak point: the password. |
| Authentication | **Password + optional keyfile** | "Something you know + something you have." New vaults derive the KEK with Argon2id over a domain-separated, length-prefixed password/keyfile encoding; legacy vaults retain their original concatenated encoding until a password change migrates the wrap. Changing the password re-wraps the master key only (no bulk re-encrypt). |
| Image decode | **stb_image** (header-only) | JPEG/PNG/GIF/BMP/TGA/HDR decoded directly from decrypted in-memory buffers. Zero dependencies, no temp files. |
| Extra image formats | **libwebp**, **libheif** + **libde265** (HEIC), **libaom** (AVIF, decoder-only) | Decode-only, vendored, cmake-built. One `decode_heif_from_memory` covers HEIC+AVIF (libheif dispatches by brand). |
| Video decode | **FFmpeg/libav** (decode-only static) | Streams video frames directly from encrypted chunks via a custom `AVIOContext` over `ChunkStore` (no temp file). Decode-only build — encoders/muxers/protocols/network all disabled. AV1 reuses the already-vendored libaom (above) as FFmpeg's `libaom-av1` decoder rather than adding a new dependency — FFmpeg's own native `av1` decoder is hwaccel-dispatch only, no software decode path. Phase 43: opportunistic hardware decode (VAAPI/D3D11VA) via FFmpeg's hwaccel dispatch, with the existing software `VideoDecodeWorker` as the automatic, silent fallback — never a hard requirement. |
| ZIP / CBZ import | **miniz** | Single-file, header-only decompression + ZIP reader, public-domain/MIT. Decompressed entries read into mlock'd `SecureBytes`, never to disk. |
| 7z / RAR / TAR import | **libarchive** + **zlib** + **xz/liblzma** | Read-only streaming archive support layered *alongside* miniz, not replacing it — `.zip`/`.cbz` keep using the proven miniz path. Read-only import of a single-volume archive only. |
| JSON parsing | **nlohmann/json** | Single-header MIT lib, header-only, no build step. Used exception-free. Sole use: an archive's optional top-level `meta.json` (gallery title + tags). |
| Thumbnails | **Pre-generated, stored encrypted in vault** | Gallery scrolling decrypts only the small thumbnail blobs — no full-image decode needed while browsing. |
| Gallery model | **Free-nesting galleries; any mix of images, videos, and sub-galleries** | A gallery may hold any combination of images, videos, and sub-galleries as direct children (Phase 46). Sub-galleries display first, then media. |
| Dependency management | **Vendored git submodules** under `vendor/` | Hermetic, reproducible, offline. See [docs/VENDORED_DEPS.md](docs/VENDORED_DEPS.md) for pinned versions, CVE review cadence, and bump procedures. |
| Primary platform | **Linux → Windows** | Owner's dev machine is Arch Linux. macOS is not supported (dropped — see `mem:tech_stack`). |

Current pinned versions, exact build commands, and the CI matrix: see `mem:tech_stack`.

## Code conventions

### C++ style
- **Standard:** C++23. Use `std::span`, designated initialisers, `[[nodiscard]]`, `constexpr` freely.
- Naming, error-handling, header, and comment conventions: see `mem:conventions`.

### Security invariants (enforce these at all times)
1. **No plaintext to disk.** Decrypted image data must never be written to any file, temp dir, or mmap'd file. Application-owned plaintext uses best-effort `mlock`'d, wipe-on-release heap buffers; opaque third-party codec/driver storage that cannot accept caller allocation must be minimized, documented, and reflected in F1's degraded status.
   - **Documented, gated exception — Export (Phase 10, `src/ui/export.*`).** This is the one feature that *deliberately* writes decrypted bytes to disk, on explicit user request. The deviation is mitigated by **consent + scope**: a per-export modal warning (`consent_dialog`, default-cancel), selection-only output (never a whole-tree dump), originals only (never thumbnails). The plaintext lives in an `mlock`'d `SecureBytes` right up to the `write()` and is `crypto_wipe`'d immediately after. No other code path may write plaintext to disk.
2. **Wipe keys on destruction.** Every buffer holding a key, KEK, or password uses `crypto_wipe` (Monocypher) before freeing.
3. **Random nonces.** Every XChaCha20-Poly1305 encrypt call uses a fresh 24-byte nonce from the CSPRNG. Never reuse nonces.
4. **Authenticate before decrypt.** Always verify the Poly1305 tag before using any plaintext bytes.
5. **No logging of key material.** Keys, passwords, and decrypted content must never appear in log output.
6. **A vault file is untrusted input; node names are path components (Phase 36).** A `.osv` is portable and shareable (vault manager, cross-vault transfer), and `index.cpp` deserialises `IndexNode::name` as opaque bytes. A name entering the vault is **validated** (`vault::is_safe_node_name` — `add_image`/`add_video`/`create_gallery` reject); a name arriving from an archive or a picked file is **repaired** (`vault::sanitize_node_name`); and a name *leaving* the vault to the filesystem is sanitized **and** the resulting path is containment-checked against the destination folder (`ui::export_path_within`). Never build an output path as `dest_dir / node.name` — `std::filesystem::path::operator/` does not contain, and an absolute name discards `dest_dir` entirely (CWE-22). Externally-supplied *paths* (file-dialog results, `vaults.list` lines) go through `platform::normalize_user_path` before they reach `fopen`.

### Hardening notes
- **Pixel data is best-effort mlock'd.** Both the *encrypted stored bytes* (a `SecureBytes`) and the *decoded* `ImageData::pixels` (a `SecureBytes` since Phase 6b — never a plain `std::vector`) are mlock'd and `crypto_wipe`'d on destruction; both draw on the same lockable budget, so a large full-res decode after reading chunks can legitimately exhaust it and degrade that one buffer to swappable. The first mlock failure per process is logged once with platform-appropriate advice (`crypto::mlock_fail_hint()`); subsequent failures stay silent (uses `should_warn_mlock_once()`). On Linux, successful mlock is followed by `madvise(MADV_DONTDUMP)` for defense-in-depth (silently ignored if it fails). At startup, `platform::grow_secure_mem_budget()` grows the lockable budget to 256 MiB: on Windows `VirtualLock` is capped by the process *minimum working-set size* (~200 KB by default — without the grow, every pixel-buffer lock silently failed), raised via `SetProcessWorkingSetSize`; on Linux the soft `RLIMIT_MEMLOCK` is raised to the hard limit. Windows caveat: `VirtualLock` keeps pages out of the pagefile but **not** out of `hiberfil.sys` — hibernation writes all resident pages to disk.
- **sws_scale destinations must be padded, never exactly-sized (Phase 80).** libswscale's vectorized writers store whole SIMD vectors per row and measurably write up to ~56 bytes past a tight (`align=1`) destination buffer at SIMD-unfriendly widths. Any new `sws_scale` call site must allocate `FFALIGN(w*bpp, 64)` linesizes **plus a ≥128-byte tail** (or write into `av_frame_get_buffer` memory, which FFmpeg pads itself) and row-copy into tight buffers afterwards. ASAN cannot catch violations — the store happens in uninstrumented vendored asm; on Windows the overrun corrupts `av_malloc`'s inter-block base pointer (`0xc0000374`), on Linux it lands silently in allocator slack. See `docs/roadmap/phase-80-poster-heap-overrun.md`.
- **stb_image allocations go through a secure, zero-initialised allocator (Phase 96b, OSV-AUD-003).** `src/image/decode.cpp` routes `STBI_MALLOC`/`STBI_REALLOC_SIZED`/`STBI_FREE` through `src/image/stb_secure_alloc.h` — a header-prefixed block that is `calloc`-zeroed (the malformed-JPEG defence: on aborted decodes stb's colour conversion reads plane regions the decode never wrote, so plain `malloc` would copy stale heap bytes — potentially previously decrypted content — into decoded pixels; the zeroed tail is preserved on grow), best-effort page-locked, and `crypto_wipe`'d before every free/realloc, honouring stb's realloc-failure contract (old block stays alive). The full-size decode therefore never leaves decrypted pixels in an unwiped, un-locked allocator. Found originally by valgrind (`--track-origins`); ASAN cannot detect in-bounds uninitialised reads, so the periodic valgrind run in README's Debugging section (targeting `decode_malformed_jpeg_returns_nullopt`) still guards the zero-init defence.
- **Thumbnail/poster intermediates are secure bytes (Phase 96, OSV-AUD-003).** Every application-owned buffer on the image-decode → thumbnail/posters → staging/transfer/migration path is `crypto::SecureBytes` (grown via the wipe-on-realloc `reserve`/`append`/`push_back` API; read out via `.as_span()`): `make_thumbnail`'s resized RGB + returned JPEG, `StagedThumb`/`StagedVideoInfo`/`VideoProbeResult` and the migration worker's `thumb_jpeg`/`poster_jpeg`, and the cross-vault transfer copies (`assign(blob.as_span())` — never a `std::vector<uint8_t>` hop). The boundary: **opaque codec internals** — libwebp's animated-decoder canvas and libheif's decoded `heif_image` planes have no caller-supplied-buffer decode API, so the codec's scratch stays library-owned (documented) while the app's copy into `SecureBytes` is secure; FFmpeg's internals are Phase D. `std::vector<uint8_t>` remains correct for ciphertext and non-secret metadata.
- **FFmpeg plaintext ownership is reference-count secured where the API permits (Phase 97, OSV-AUD-003).** `src/media/ffmpeg_secure.*` replaces packet/software-frame `AVBufferRef`s with wrappers that page-lock the underlying allocation and wipe it only from the wrapper's final-release callback; never wipe a buffer merely because one packet/frame reference is being unref'd. Codec contexts install `secure_get_buffer2`; filter and hardware-transfer outputs are wrapped after allocation. AVIO buffers wipe the actual final `AVIOContext::buffer`; PCM/animated RGBA use `SecureVector`, and poster/GIF/published-frame storage uses `SecureBytes`. Opaque FFmpeg codec/filter scratch, GPU surfaces, and SDL audio-stream copies cannot be fully governed by app allocators, so using the pipeline marks `secure_memory_degraded()` and F1 reports the limitation. Preserve the Phase 80 padding rule at every swscale destination.
- **Core dumps are disabled in Release builds.** At app startup (Release only), `prctl(PR_SET_DUMPABLE, 0)` + `setrlimit(RLIMIT_CORE, 0)` (Linux) prevent core dumps from capturing decrypted data. Debug builds keep dumps + ptrace attach enabled. (Windows is a no-op here; macOS support has been removed.)
- **Password change is not crash-safe.** Avoid force-killing the app during password re-wrap (a KEK change without bulk re-encrypt); recovery would require manual recovery steps.
- **Framed vaults reveal plaintext *compressibility* through ciphertext length (Phase 26)** — accepted for the local-attacker threat model.
- **Batched import commits (Phase 50):** a crash mid-import loses at most the last commit batch's index entries; the orphaned chunks are dead ciphertext reclaimed by `Shift+C` compact. Integrity and the 3-phase slot swap are unchanged.
